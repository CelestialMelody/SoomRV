## 风险点
### 1.BTUpdate 多源仲裁是“最后有效覆盖”而非显式优先级协议，可能吞掉同拍更新。
证据: for 循环覆盖 btUpdate，后出现的 valid 覆盖前者，IN_btUpdates 又由三路拼接输入。
参考: src/BranchPredictor.sv:79, src/IFetch.sv:116.

### 2.fetchLimit 通过 stall 防止 PC/BP 文件被覆盖，若高压分支提交+取指并发，前端可能出现明显吞吐抖动。
证据: fetchLimit命中即 OUT_stall=1。
参考: src/BranchPredictor.sv:278, src/IFetchPipeline.sv:153, src/IFetchPipeline.sv:154.

### 3.ignorePred 恢复窗口期间，预测器输出切换到 recoveredPC，若恢复数据（PCFile/BPFile）延迟/竞争，可能出现1拍空转或错误路径短暂可见。
参考: src/BranchPredictor.sv:105, src/BranchPredictor.sv:107, src/BranchPredictor.sv:303.

### 4.“multiple branch in one fetch bundle” 依赖 BTB 的 multiple 延迟写标记（setMult），同拍冲突时行为较脆弱。
参考: src/BranchTargetBuffer.sv:96, src/BranchTargetBuffer.sv:123.

### 5.predIllegal（预测落在32位指令前半字）会触发重抓与BTB清理，若频繁发生会造成前端重复flush。
参考: src/BranchHandler.sv:307, src/BranchHandler.sv:354, src/BranchHandler.sv:479.
