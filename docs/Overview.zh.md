# 总体架构
SoomRV 是一个基于标签的乱序架构。在重命名阶段，每个写入架构寄存器（即虚拟寄存器）的指令都会被分配一个标签。这个标签既用作指令本身的目标寄存器，也用作所有依赖于该计算值的指令的源寄存器。只有当新指令写入同一虚拟寄存器并提交时，标签才会被释放。当前推测的以及已提交的虚拟寄存器到物理寄存器的映射都存储在 [RenameTable](../src/RenameTable.sv) 中。

指令重命名后，它们会在各个发射队列中等待执行。在发射队列内，使用操作数标签来跟踪指令操作数的可用性。一旦所有操作数都可用，指令就会被发射，即使较旧的指令仍在等待中。

操作数的实际值目前不会存储在 IQ 中（立即数除外）。操作数寄存器只在指令发射后的下一个"加载"流水线阶段加载。

指令以推测方式和乱序方式执行。因此，在出现错误推测时需要恢复机制。SoomRV 使用重排序缓冲区来跟踪所有重命名后的指令。如果发生错误推测，会触发全局 `branch` 信号。该信号会使流水线各阶段和 ROB 中所有错误推测后的在途指令无效。为了检查给定指令是在错误推测之前还是之后，每个指令都携带一个序列号。

此外，在错误推测后，重命名状态的恢复是必要的。在 SoomRV 中，当错误推测触发时，重命名状态会重置为已提交状态。然后，未提交的指令会从 ROB 中"重放"以恢复最后正确的重命名状态。（另一种可能的方法是在每个周期对重命名状态进行快照。）

# 微操作 (UOps)
SoomRV 的大部分架构都是围绕不同模块之间传递各种 `UOp` 或其他结构体构建的。

这些结构体（和其他数据类型）的定义在 [src/Include.sv](../src/Include.sv) 中。

下面显示的是 `EX_UOp`（"执行微操作"），这是功能单元在执行流水线阶段接收到的微操作。

```systemverilog
typedef struct packed
{
    logic[31:0] srcA;
    logic[31:0] srcB;
    logic[31:0] pc;
    FetchOff_t fetchOffs;
    FetchOff_t fetchStartOffs;
    FetchOff_t fetchPredOffs;
    logic[31:0] imm;
    logic[5:0] opcode;
    Tag tagDst;
    SqN sqN;
    FetchID_t fetchID;
    BranchPredInfo bpi;
    SqN storeSqN;
    SqN loadSqN;
    FuncUnit fu;
    logic compressed;
    logic valid;
} EX_UOp;
```

以下是一些最重要字段的简要说明。虽然以 `EX_UOp` 为例，但这些字段几乎在所有 UOp 结构体中都能找到。

### `sqN`（序列号）
在重命名阶段，所有指令都会被分配一个唯一的标识符，以序列号的形式表示。

序列号的长度比重排序缓冲区的索引多一位，这使我们能够使用二进制补码算术来比较任意两个在途指令的顺序。

这通常用于在分支或其他错误预测期间使微操作无效，使用类似于下面显示的代码。

```systemverilog
if (IN_uop.valid && (!IN_branch.taken || $signed(IN_uop.sqN - IN_branch.sqN) <= 0)) begin
    // 有效的微操作
end
```

较低的序列号位用作在放置或修改指令条目时重排序缓冲区的索引。

因此，在 ROB 中，只有最重要的 `SqN` 位是显式存储的。所有其他位都由索引隐式给出。

### `loadSqN`、`storeSqN`（加载和存储序列号）
与用作 ROB 索引的 `sqN` 类似，这些分别用作 LoadBuffer 和 StoreQueue 的索引。

### `tagDst`（目标寄存器标签）
除了序列号，重命名还会为指令分配一个目标寄存器来存储其结果。这类似于 RISC-V 中的 `rd`，但指的是实际的物理寄存器而不是虚拟寄存器。

### `fetchID`
获取 ID 类似于序列号，不过它是在获取阶段分配的；与SqN不同，SqN在重命名阶段较晚才分配。

获取 ID 用于访问为每个获取束存储在 PCFile 中的获取状态备份。

具体来说，当我们想要知道指令的程序计数器或分支预测信息时，我们会访问获取状态备份。这些信息只存储在 PCFile 中，从而节省了面积。

在 `EX_UOp` 的情况下，这种访问已经由紧接在前面的流水线阶段（Load）为我们执行，以便在执行期间使用。

此外，如果指令是异常或预测分支，ROB 将使用指令的 `fetchID` 访问 PCFile。在这两种情况下，我们都需要在提交后访问原始程序计数器。

# 模块
以下是 SoomRV 中一些重要模块的简要描述。

下面的大多数模块本身都在 [Core](../src/Core.sv) 模块内实例化。

### [IFetch](../src/IFetch.sv)
IFetch 是一个大型模块，处理前几个流水线阶段，所有与指令获取相关的操作。它还包含所有分支预测模块。

IFetch 输出一个获取束（`IF_Instr`），它（取决于对齐和分支）包含最多8个半字的指令数据（16字节）。

#### [BranchPredictor](../src/BranchPredictor.sv)
在每个周期中，基于当前程序计数器和分支预测状态预测下一个程序计数器。我们每个周期最多预测一个分支，无论是否采用。

分支预测处理目标预测（[`BranchTargetBuffer`](../src/BranchTargetBuffer.sv)）和方向预测（[`TagePredictor`](../src/TagePredictor.sv)）。此外，[`ReturnStack`](../src/ReturnStack.sv) 处理返回预测。

#### [BranchHandler](../src/BranchHandler.sv)
一旦指令从 ICache 加载，BranchHandler 会通过将早期预测与实际指令进行比较来修正早期预测。例如，如果由于分支别名导致跳转目标错误，BranchHandler 会进行修正。几乎所有内容都可以被修正，
除了条件分支方向和间接分支目标，这些在执行期间处理。其他所有内容，特别是直接跳转目标 & 条件分支目标，在 BranchHandler 之后保证正确，无需在下游检查。

#### PCFile & BPFile
PCFile 存储每个获取束的源程序计数器，BPFile 存储其分支预测状态。分支预测状态包括分支历史，以及束中的哪个指令被预测为分支（如果有的话）。这些文件用于在错误预测后重置前端状态。获取束的 PCFile 和 BPFile 条目在其所有指令提交后被释放。

### [PreDecode](../src/PreDecode.sv)
PreDecode 是一个缓冲区，同时将 IFetch 的指令束分割为一个或多个离散的
16或32位指令（在 RISC-V 中，这基于指令的低两位）。

然后将各个指令分发到解码器端口。

### [InstrDecoder](../src/InstrDecoder.sv)
在解码器中，RISC-V 的指令格式被解码为 SoomRV 的内部格式。

### [Rename](../src/Rename.sv)
在重命名模块中，我们为指令分配 `sqN` 和 `tagDst`。操作数寄存器也使用 RenameTable 重命名为相应的标签。

一些指令甚至被消除，即在重命名阶段内完全执行。例如，这包括 NOP 或小立即数的加载。

### [IssueQueue](../src/IssueQueue.sv)
来自重命名的指令被放入发射队列。在那里，指令等待直到所有操作数和功能单元都准备好执行。一旦准备好，微操作就会被发射，即从发射队列中出队。

可能，来自重命名的指令会被放入_多个_发射队列，
以生成多个微操作。这目前只被读-修改-写原子指令使用。
这使得 `IssueQueue` 成为从指令到微操作的正式转换，尽管我们使用这些术语非常宽松。

### [Load](../src/Load.sv)
微操作发射后，其操作数必须被加载。
这是由 Load 完成的，它访问寄存器文件和/或转发操作数。
为了减少重复的操作码，Load 可以使用 `immB` 字段被指示使用立即值作为第二个操作数（而不是寄存器）。

Load 也会访问 PCFile，以防指令在执行期间需要知道其程序计数器或分支预测状态。
通过在 Load 中从 PCFile 重新加载这些信息，我们不必将其存储在发射队列中。

### 执行
执行在各种功能单元中发生。通常，这些只是计算结果并将其写入寄存器文件。此外，一些 FU 还处理分支和内存访问。

#### [IntALU](../src/IntALU.sv)
这是整数计算的首选位置。它还处理所有分支，
除了不带链接寄存器的立即跳转。这些由解码器处理，因为它们不从寄存器读取或写入寄存器。

分支目标信息从 `IntALU` 通过 `BTUpdate` 结构体发送到分支预测器。
分支_方向_信息的发送推迟到提交时，以避免被推测执行的分支污染。

#### [AGU](../src/AGU.sv)
AGU 执行地址计算和转换。之后，它们将加载/存储微操作转发到内存子系统的相应功能单元。

### [ROB](../src/ROB.sv)
执行完成后，指令在 ROB 中被标记为已完成。如果所有先前的指令都已提交，并且没有错误预测，ROB 最终会提交指令。

虽然指令的 ROB 条目只有在指令执行后才准备好提交，但条目在重命名后就已经创建了。这是必需的，因为 ROB 用于在错误预测后恢复重命名状态。

ROB 还为每条指令存储标志。在指令执行期间可以设置标志以调整提交行为。例如，`FLAGS_ILLEGAL_INSTR` 可以被设置以在提交后触发异常；而 `FLAGS_ORDERING` 会在继续执行之前刷新流水线。

### [LoadBuffer](../src/LoadBuffer.sv)
加载缓冲区存储每个已执行但尚未提交的加载。这用于检测加载顺序错误预测（如果加载在它所依赖的存储之前执行）。

我们还使用 LoadBuffer 来存储延迟的加载，直到它们准备好执行。

### [StoreQueue](../src/StoreQueue.sv)
存储队列存储每个已执行的存储。存储提交后，它会被移交给 StoreQueueBackend。

此外，存储队列将存储的数据转发给加载。所有非 MMIO 加载在从缓存读取的同时在存储队列中查找。

### [StoreQueueBackend](../src/StoreQueueBackend.sv)
SQB 本质上充当存储的发射队列，与其他发射队列的区别在于存储可能在_提交后_执行，因为它们没有回滚机制。SQB 从 SQ 接收已提交的存储，然后融合并执行它们。所有发送到相同16字节区域的存储都被融合，因为缓存写端口是16字节宽。这也很方便地消除了存储别名检查的需要。

### [LoadStoreUnit](../src/LoadStoreUnit.sv)
LSU 在低级处理内存访问。它通过访问缓存执行加载和存储，如果发生缓存缺失也会处理缓存缺失。

进入 LSU 的所有存储都来自存储队列。加载通常直接从加载 AGU 进入，但也可能来自 LoadBuffer 或 PageWalker。

#### [BypassLSU](../src/BypassLSU.sv)
BLSU 处理外部 MMIO。它不读取缓存，而是直接与内存控制器通信以访问 MMIO 设备。它也可用于实现未来绕过缓存的常规加载/存储。

### [MemoryController](../src/MemoryController.sv)
内存控制器处理缓存和主内存之间缓存线的传输。
与所有其他模块不同，它在 SoomRV `Core` 模块外部实现。
目前，使用自定义32位双向内存总线，这是在 OpenMPW shuttle 上 IO 数量有限的情况下实现的。该总线将被标准 Wishbone 或 AXI 总线取代。
