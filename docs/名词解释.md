# SoomRV 名词解释

本文档收集对 SoomRV 中重要结构、模块、概念的单独解释，便于查阅。

**文档约定**：解释中提到的**变量、信号、模块**会一并说明含义，并标注**代码位置**（文件路径 + 行号或行号范围），方便不熟悉代码的读者对照阅读。涉及 SoomRV 代码中的**结构体字段、常量、类型名**时，会做**简要解释**（含义与定义位置）。例如提到「deqCandidate」「PriorityEncoder」时，会在文中写出它们是什么、在哪个文件的哪几行定义或使用。

**关于「槽」**：文档中的**槽**（slot）指**某个数组或队列中的一个位置（下标）**，即「第几个格子/条目」。常见两种用法：(1) **队列中的槽**：如 IssueQueue 的 `queue[i]`、「槽 i」= 队列中下标为 i 的那一条记录；(2) **一拍内多条 uop 的槽**：如 Rename 每拍输出多条 R_UOp，「槽 i」= 第 i 条（IN_uop[i]）。二者都表示「用下标 i 标识的那一个位置/条目」。

## 取指与 IF_Instr 相关名称（FETCH_WORDS、fetchID、firstValid、lastValid）

以下名称在取指与 **IF_Instr** 结构体中常用，解释与代码位置如下。

| 名称 | 含义 | 定义/位置 |
|------|------|-----------|
| **FETCH_WORDS** | 一次取指包内**半字（16 位）的个数**；IF_Instr 的 `instrs` 数组长度为 FETCH_WORDS。 | `Config.sv` 第 19 行：`parameter FETCH_WORDS = 1 << (\`FSIZE_E - 1);`；`FSIZE_E` 为 4 时等于 8。 |
| **FSIZE_E** | 取指块大小的指数（2^FSIZE_E 为相关粒度），用于推导 FETCH_WORDS、FetchOff_t 位宽等。 | `Config.sv` 第 17 行：`define FSIZE_E 4`。 |
| **FetchID_t** | **取指包 ID** 的类型；同一次取指的一批指令共享同一 fetchID，用于分支恢复、flush 时定位。 | `Include.sv` 第 6 行：`typedef logic[4:0] FetchID_t;`（5 位）。 |
| **fetchID** | IF_Instr（及后续 PD_Instr、D_UOp 等）的字段，表示**本包/本条指令所属的取指包 ID**。 | `Include.sv` 第 538 行（IF_Instr）、第 553 行（PD_Instr）等。 |
| **FetchOff_t** | 取指包内**半字偏移**的类型；表示「第几个半字」（0 到 FETCH_WORDS-1）。 | `Include.sv` 第 7 行：`typedef logic[\`FSIZE_E-2:0] FetchOff_t;`（FSIZE_E=4 时为 3 位）。 |
| **firstValid** | 本取指包中**有效半字的起始下标**（FetchOff_t）；仅 `instrs[firstValid]..instrs[lastValid]` 有效。 | `Include.sv` 第 540 行（IF_Instr 内）。 |
| **lastValid** | 本取指包中**有效半字的结束下标**（FetchOff_t）；与 firstValid 共同界定本包有效范围。 | `Include.sv` 第 541 行（IF_Instr 内）。 |
| **instrs** | IF_Instr 的**半字数组**，`instrs[FETCH_WORDS-1:0][15:0]`，即 8 个 16 位半字（默认）。 | `Include.sv` 第 545 行。 |

**IF_Instr** 完整定义见 `Include.sv` 第 535–548 行；除上述字段外还有 pc、IFetchFault、predPos、predTaken、predTarget、valid 等。

## fetchOffs、fetchStartOffs、fetchPredOffs 与 bpi（取指/分支预测相关字段）

这些字段在 **EX_UOp**、**PCFileEntry**、**BranchProv**、**BTUpdate** 等中用于**定位指令在取指包中的位置**以及**分支预测方向**，供分支解析、mispred 判定和预测器更新使用。

**fetchOffs**  
- **含义**：本条指令在**取指包内的半字偏移**（FetchOff_t），即「这条指令对应取指包中第几个半字」；通常表示指令**当前/最后**半字的位置（RISC-V 中 PC 常存最后半字，下一指令 +1）。  
- **类型**：`FetchOff_t`（`Include.sv` 第 7 行，约 3 位）。  
- **使用**：**Load.sv** 第 117 行用 `outUOpReg[i].fetchOffs` 与 **IN_pcReadData[i].branchPos** 比较，相等时才把 **bpi** 填到 EX_UOp（表示本条就是预测器认为的分支所在指令）；**IntALU.sv** 第 200 行把 **fetchOffs** 带入 **BranchProv**，用于 flush/恢复时定位。

**fetchStartOffs**  
- **含义**：本条指令在取指包内的**起始**半字偏移，即指令**第一个**半字在包中的下标。与 fetchOffs 区别：32 位指令占两个半字，fetchStartOffs 指第一个，fetchOffs 可能指最后一个。  
- **来源**：**PCFile** 中按 fetchID 存了每条指令的 pc；pc 低段含有起始偏移。**Load.sv** 第 118 行 `OUT_uop[i].fetchStartOffs = IN_pcReadData[i].pc[$bits(FetchOff_t)-1:0]`，即从 PCFile 读出的 pc 的低位。  
- **使用**：**IntALU.sv** 第 235 行、**BranchHandler.sv** 多处：**BTUpdate** 的 **fetchStartOffs** 告诉 BTB/预测器「这条分支指令在取指包中的起始位置」，用于更新目标或索引。

**fetchPredOffs**  
- **含义**：**预测器认为的分支所在位置**——即在该取指包（fetchID）内，预测器记录的分支指令所在的半字偏移（branchPos）。  
- **来源**：**Load.sv** 第 119 行 `OUT_uop[i].fetchPredOffs = IN_pcReadData[i].branchPos`；**PCFileEntry**（`Include.sv` 第 501 行）中有 **branchPos**，表示该 fetch 包中「分支预测所对应的位置」。  
- **使用**：**IntALU.sv** 第 236–237 行：间接跳转（JALR/JR）时，若实际分支位置与预测位置不同，**btUpdate_c.multiple** 与 **multipleOffs = fetchPredOffs + 1** 用于更新 BTB（多条候选等）；与 **fetchStartOffs** 一起区分「预测的是哪条指令」。

**bpi（BranchPredInfo）**  
- **含义**：**分支预测信息**，目前仅包含**方向预测**：**taken**（1=预测跳转，0=预测不跳）。取指/预解码阶段对该条指令做的「跳/不跳」预测，在分支执行时与**实际结果**比较，若不同则产生 mispred。  
- **类型**：`Include.sv` 第 415–418 行 `typedef struct packed { logic taken; } BranchPredInfo;`  
- **来源**：**PCFile** 按 fetchID 存了该包内分支位置的 **bpi**；**Load.sv** 第 116、120–121 行：仅当 `outUOpReg[i].fetchOffs == IN_pcReadData[i].branchPos` 时（即本条就是预测器认为的分支指令）才把 **IN_pcReadData[i].bpi** 填到 **OUT_uop[i].bpi**。  
- **使用**：**IntALU.sv** 第 207 行 `if (branchTaken != IN_uop.bpi.taken && IN_uop.opcode != BR_JAL)` 判断方向错误；第 223 行 `!IN_uop.bpi.taken` 用于间接跳转的恢复；分支提交时用实际方向更新预测器（ROB 的 BPUpdate 等）。

**小结**  
| 名称 | 含义 | 主要用途 |
|------|------|----------|
| **fetchOffs** | 本条指令在取指包内的半字偏移（当前/最后半字） | 拼 PC、与 branchPos 比较以填 bpi、BranchProv 定位 |
| **fetchStartOffs** | 本条指令在取指包内的**起始**半字偏移 | BTUpdate 告诉预测器分支指令位置 |
| **fetchPredOffs** | 预测器记录的分支所在半字偏移（branchPos） | 与 fetchStartOffs 比较、BTUpdate 的 multipleOffs |
| **bpi** | 分支方向预测（taken/not taken） | 与实际 branchTaken 比较判 mispred、更新预测器 |

## 槽（slot）

**是什么**  
文档里的**槽**指**某个数组或队列中的一个位置（下标）**，即「第几个格子/条目」，对应代码里的下标 `i`（如 `queue[i]`、`IN_uop[i]`）。

**两种常见用法**  
1. **队列中的槽**：如 IssueQueue 的 `queue[SIZE-1:0]`，「槽 i」= `queue[i]`，即队列中**下标为 i 的那一条记录**；「有效槽」= 下标在 `0 .. insertIndex-1` 的条目；「被选中的槽」= 本周期出队的那个下标 `deq.idx`。  
2. **一拍内多条 uop 的槽**：如 Rename 每拍输出 `IN_uop[0]..IN_uop[WIDTH_ISSUE-1]`，「槽 i」= 第 i 条 uop（`IN_uop[i]`）；解码器、IssueQueue 入队等也常用「槽」表示「第几条」或「第几个端口/位置」。

**小结**  
| 用法 | 含义 |
|------|------|
| 队列中的槽 | 队列数组的一个下标位置，如 IssueQueue 的 queue[i]、ROB 的某 entry |
| 一拍内多条的槽 | 固定宽度阶段输出中的第 i 条，如 IN_uop[i]、RN_uop[i] |

## sqN、storeSqN、loadSqN（序列号与 Load/Store 顺序）

**sqN（Sequence Number）**  
- **含义**：**全局程序顺序序列号**。每条指令在重命名时被分配一个单调递增的 **sqN**，用于在乱序流水线中表示「谁先谁后」：ROB 按 sqN 排序提交、分支错误预测时用 sqN 比较「是否在错误路径上」、部分结构用 sqN 做容量或顺序检查。  
- **类型与定义**：`Include.sv` 第 4 行 `typedef logic[\`ROB_SIZE_EXP:0] SqN;`；`ROB_SIZE_EXP` 在 `Config.sv` 第 38 行为 6，故 SqN 为 7 位。  
- **赋值**：在 **Rename.sv** 中，每拍对成功输出的每条 R_UOp 分配 `counterSqN`，然后递增（约 259、274、291、376 行）；mispred 恢复时从 `IN_branch.sqN` 重新对齐。

**storeSqN**  
- **含义**：本条指令**对应的 store 计数**（「到本条为止已分配了多少条 store」）。对 **Store** 指令而言，即本 store 在 store 序列里的编号；对 **Load** 指令而言，即「排在本 load 之前的 store 数量」。用于：Load 与前面 Store 的顺序/依赖（如 LoadBuffer、Store 转发）、Store 是否可发射（不超过 StoreQueue 容量）等。  
- **在 R_UOp 中的位置**：`Include.sv` 第 599、605 行（R_UOp）、627、672、730 等（IS_UOp、EX_UOp、AGU_UOp、LD_UOp 等一路传递）。  
- **赋值**：**Rename.sv** 第 220、224、229、234–235、345 行：`storeSqNs[0]=counterStoreSqN`，遇 Store/Atomic 时 `storeSqNs[i+1]=storeSqNs[i]+1`；R_UOp 的 **storeSqN** 取 `storeSqNs[i+1]`（注释：store 用「先递增」后的值，即本 store 的序号）。

**loadSqN**  
- **含义**：本条指令**对应的 load 计数**（「到本条为止已分配了多少条 load」）。对 **Load** 指令而言，即本 load 在 load 序列里的编号；对 **Store** 而言，即「排在本 store 之前的 load 数量」。用于：Store 与前面 Load 的顺序、Load 是否可发射（不超过 LoadBuffer 容量）、load/store 冲突检测等。  
- **在 R_UOp 中的位置**：`Include.sv` 第 600、606 行（R_UOp）及后续 IS_UOp、EX_UOp、AGU_UOp、LD_UOp 等。  
- **赋值**：**Rename.sv** 第 219、223、228、233、346 行：`loadSqNs[0]=counterLoadSqN`，遇 Load/Atomic 时 `loadSqNs[i+1]=loadSqNs[i]+1`；R_UOp 的 **loadSqN** 取 `loadSqNs[i]`（注释：load 用「后递增」前的值，即本 load 的序号）。

**小结**  
| 名称 | 含义 | 主要用途 |
|------|------|----------|
| **sqN** | 全局程序顺序序列号，每指令唯一 | ROB 排序、mispred 比较、顺序/容量检查 |
| **storeSqN** | 到本条为止的 store 计数（本条若是 store 则含自己） | Load 与前面 Store 的顺序、StoreQueue 容量、Store 转发 |
| **loadSqN** | 到本条为止的 load 计数（本条若是 load 则含自己） | Store 与前面 Load 的顺序、LoadBuffer 容量 |

## availA/tagA、availB/tagB（操作数就绪与依赖 tag）

在 **R_UOp**、**IS_UOp** 以及 IssueQueue 内部的 **R_ST_UOp** 中，源操作数不用「寄存器名」或「数值」表示，而是用**物理 tag + 就绪位**表示依赖关系。

**tagA / tagB**  
- **含义**：本条指令**第一个 / 第二个源操作数**所依赖的**物理结果 tag**。通常 **tagA** 对应 rs1、**tagB** 对应 rs2；若某源是立即数或常数（如 x0），则用特殊 tag 编码（如 **TAG_ZERO** 或 tag 高位为 1 的立即数编码）。  
- **类型**：`Tag`（`Include.sv` 约 2 行，`logic[RF_SIZE_EXP:0]`），与 RegFile/写回总线、forward 的 tag 一致。  
- **赋值**：**Rename.sv** 中由 RenameTable 查表得到：rs1 → **tagA**，rs2 → **tagB**（约 329–332 行 `RAT_lookupSpecTag[2*i+0/1]`）。  
- **使用**：**Load.sv** 用 **tagA/tagB** 做两件事：(1) 在 **forwards** 数组中按 tag 匹配，若匹配则 srcA/srcB 取前递结果（约 55–57、62、166、180 行）；(2) 若无前递则向 RegFile 发读请求 **OUT_rfReadReq[i].tag = tagA**（或 tagB）（约 82–88 行）。若 tag 高位为 1，则按立即数/常数解释（约 161–163、175–177 行）。

**availA / availB**  
- **含义**：**该源操作数是否已就绪**。`avail=1` 表示「该 tag 对应的结果已经存在」——要么已写回 RegFile，要么本周期/前几拍会在写回或前递总线上出现，下游可以直接从 RegFile 或 forward 取到值；`avail=0` 表示「还在等某条指令写回该 tag」，不能发射。  
- **类型**：单比特 `logic`（`Include.sv` 第 617、619 行，IS_UOp 内）。  
- **赋值**：**Rename.sv** 中初值来自 RenameTable 的 **RAT_lookupAvail**（约 329–332 行）；若某条指令完成写回（**IN_flagsUOps[i].tagDst**），Rename 会把自己输出的、**tagA/tagB 等于该 tagDst** 的条目的 **availA/availB** 置 1（约 305–308 行）。在 **IssueQueue** 内部，队列项也维护 **avail**，并随写回/前递总线每拍更新；只有 **所有操作数 avail 均为 1** 的条目才可能被选为 **deqCandidate** 发射出去。  
- **使用**：**IssueQueue** 用 **queue[i].avail**（与 tag 对应）判断「能否发射」；发射出的 **IS_UOp** 仍带 **availA/availB**，但 **Load** 阶段不依赖这两位的值，只根据 **tagA/tagB** 去查 forward 或读 RegFile。

**为何叫“tag 版”操作数**  
R_UOp/IS_UOp 里**不存**操作数的实际数值（如 32 位 data），只存「等谁」（tagA/tagB）和「等到了没有」（availA/availB）。这样 IssueQueue 只需按 tag 匹配写回/前递即可更新就绪状态；真正取数发生在 **Load** 阶段，用 tag 查 RegFile 和 forward 得到 **srcA/srcB** 后填入 **EX_UOp**。

**小结**  
| 名称 | 含义 | 定义位置 | 主要用途 |
|------|------|----------|----------|
| **tagA / tagB** | 第一/第二源操作数依赖的物理 tag（rs1/rs2→tagA/tagB） | Include.sv 618、620 行（IS_UOp）等 | Load 用其查 forward、发 RegFile 读、或解立即数 |
| **availA / availB** | 该源操作数是否已就绪（1=可取值） | Include.sv 617、619 行（IS_UOp）等 | IssueQueue 判断能否发射；Rename 随写回更新 |

## AGU（Address Generation Unit，地址生成单元）

**是什么**  
**AGU**（Address Generation Unit，**地址生成单元**）是负责**访存指令的地址计算与地址侧处理**的功能单元。Load/Store 指令在 Load 阶段得到真实的 **srcA**（通常为基址）、**srcB**（通常为偏移或立即数）后，作为 **EX_UOp** 送入 AGU；AGU 计算**有效地址**（如 `addr = srcA + srcB`），根据 opcode 确定访问宽度（byte/halfword/word）、符号扩展、写掩码（Store），并请求 **DTLB** 做虚址到物理地址翻译；若有权限/缺页则产生异常；最终输出 **AGU_UOp**（带 addr、isLoad/isStore、size、wmask、tagDst、sqN 等）给 LoadBuffer/StoreQueue，以及 **ELD_UOp**（早期 load 地址，用于 VIPT 等）。

**在流水线中的位置**  
- 输入：**EX_UOp**（来自 Load 阶段，已含 srcA、srcB、opcode、fu 等）。  
- 输出：**AGU_UOp**（访存请求）→ LoadBuffer（Load）或 StoreQueue（Store）；**ELD_UOp** → LSU 用于早期地址；**FlagsUOp**（异常时）。  
- 与 TLB/MMU：AGU 发出 **OUT_tlb**（TLB_Req），接收 **IN_tlb**（TLB_Res）；缺页时通过 **OUT_pw** / **IN_pw** 与 PageWalker 交互。

**代码位置**  
- 模块定义：`src/AGU.sv`。  
- 地址计算：第 43 行 `wire[31:0] addr = IN_uop.srcA + IN_uop.srcB;`；第 50–66 行组装 **aguUOp_c**（valid、addr、tagDst、sqN、storeSqN、loadSqN 等）；第 68–100 行根据 opcode 区分 Load（LSU_LB/LH/LW/…）与 Store（LSU_SB/SH/SW/…），设置 size、signExtend、wmask 等。  
- **NUM_AGUS**：`Config.sv` 第 94 行 `parameter NUM_AGUS = 2`，即 2 个 AGU 端口；**FU_AGU** 为 `FuncUnit` 枚举（`Include.sv`），Load/Store 指令的 `fu` 为 FU_AGU，解码后进入 AGU 对应的 IssueQueue 端口。

**小结**  
| 项目 | 说明 |
|------|------|
| 全称 | Address Generation Unit（地址生成单元） |
| 作用 | 访存指令的地址计算（addr=srcA+srcB）、宽度/掩码/符号扩展、DTLB 请求、输出 AGU_UOp/ELD_UOp |
| 输入/输出 | EX_UOp → AGU → AGU_UOp（→ LoadBuffer/StoreQueue）、ELD_UOp、FlagsUOp（异常） |
| 配置 | NUM_AGUS=2（Config.sv）；模块见 src/AGU.sv |

## LSU（Load Store Unit，加载存储单元）

**是什么**  
**LSU**（Load Store Unit，**加载存储单元**）是执行**实际访存**的模块：接收来自 LoadBuffer/StoreQueue 的 **LD_UOp**（Load 请求）和 **ST_UOp**（Store 请求），对 **D-Cache** 发起读/写，处理 cache hit/miss、与 MemoryController 交互；对落在 **MMIO** 地址范围的访问则走 **BypassLSU**，不经过 cache，直接与 SoC 的 MMIO 接口交互。LSU 还负责 Store 转发给 Load（StFwdResult）、Load 结果写回（ResultUOp/FlagsUOp）、以及 MMIO 的读写完成与 stall。

**在流水线中的位置**  
- 上游：Load 路径为 **LoadBuffer** 输出的 LD_UOp；Store 路径为 **StoreQueue** 输出的 ST_UOp。  
- 下游：D-Cache 读/写（**IF_cache**）、**IF_mmio**（MMIO 读写）、**MemController**（cache 未命中时访问内存）；Load 结果经 **OUT_resultUOp/OUT_flagsUOp** 写回；Store 完成经 **OUT_stAck** 等。  
- 模块：**LoadStoreUnit** 在 `src/LoadStoreUnit.sv`；MMIO 旁路在 `src/BypassLSU.sv`；Core/SoC 中 LSU 与 Cache、MMIO、MemoryController 的连线见 `Core.sv`、`SoC.sv`。

**小结**  
| 项目 | 说明 |
|------|------|
| 全称 | Load Store Unit（加载存储单元） |
| 作用 | 对 D-Cache 做 Load/Store 读写、cache 未命中时访问内存；MMIO 地址走 BypassLSU |
| 输入/输出 | LD_UOp、ST_UOp → LSU → Cache/MMIO/MemController；ResultUOp、FlagsUOp、ST_Ack 等 |
| 代码 | src/LoadStoreUnit.sv；BypassLSU.sv（MMIO 路径） |

## MMIO（Memory-Mapped I/O，内存映射 I/O）

**是什么**  
**MMIO**（Memory-Mapped I/O，**内存映射 I/O**）指把**设备寄存器**映射到处理器**同一套地址空间**里，用普通的 **Load/Store 指令**访问：某段物理地址不指向 RAM，而是指向定时器、中断控制器、UART 等外设的寄存器；访问这些地址时**不经过 D-Cache**，由 SoC 路由到对应设备，读写产生副作用（如清中断、改配置）。SoomRV 中若 Load/Store 的地址落在 MMIO 范围，会走 **BypassLSU**，与 **MMIO** 模块（`src/MMIO.sv`）或外部 MMIO 接口交互，而不写 cache。

**地址范围（SoomRV）**  
- **IS_MMIO_PMA(addr)**：`Config.sv` 第 47–48 行，`(addr) < 32'h8000_0000` 的地址视为 MMIO（即高 2G 为“可能内存”，低 2G 为“可能 MMIO”，具体再按区间区分）。  
- 内部 MMIO：如 **SYSCON_ADDR**（0x1110_0000）、**MTIME_ADDR**（0x1100_bff8）、**MTIMECMP_ADDR**（0x1100_4000）等（第 54–56 行）。  
- 外部 MMIO：可选 **EXT_MMIO_START/END**（如 0x1000_0000–0x1100_0000，第 71–72 行）。  
- LD_UOp/ST_UOp 中的 **isMMIO** 字段（`Include.sv` 等）表示该次访问是否为 MMIO，LSU 据此选择走 cache 还是 BypassLSU。

**小结**  
| 项目 | 说明 |
|------|------|
| 全称 | Memory-Mapped I/O（内存映射 I/O） |
| 含义 | 设备寄存器占一段物理地址，用 Load/Store 访问，不经过 D-Cache，走 BypassLSU/MMIO 模块 |
| SoomRV | 地址 &lt; 0x8000_0000 可视为 MMIO；内部/外部区间见 Config.sv；LD_UOp/ST_UOp 有 isMMIO |

## IssueQueue（发射队列）

**是什么**  
IssueQueue（发射队列）是 SoomRV 里实现**动态调度**的部件：重命名后的指令（R_UOp）按**功能单元类型**进入不同队列，在队列里只保存「用 tag 表示的操作数依赖」；当某条指令的**所有操作数就绪**且**对应功能单元有空**时，从队列**发射**出去，变为 IS_UOp，进入 Load 阶段读寄存器再进入执行阶段。  
即：**IssueQueue = 按 FU 分类的等待队列 + 就绪判断 + 每周期选一条发射**。

**在流水线中的位置**  
```
Rename → [R_UOp] → 各 IssueQueue（按 fu 和端口入队）
                        ↓
                   就绪则出队 → [IS_UOp] → Load（读 RegFile/forward）→ [EX_UOp] → 各 FU
```

- **入队**：Rename 输出的 R_UOp 根据 `fu` 和 `validIQ[PORT_IDX]` 进入对应端口的 IssueQueue（以及 Store 数据用 StoreDataIQ）。
- **出队**：每个 IssueQueue 根据「操作数 tag 是否都就绪」和「本端口 FU 是否可用」算出一组**出队候选**（`deqCandidate_c`），用 **PriorityEncoder** 在其中选一个下标，得到**被选中的那条**（`deq`），输出一条 IS_UOp；下一级是 Load，再下一级是各 FU（IntALU、AGU、Mul、Div 等）。

**关键逻辑与代码位置**

- **队列内容**  
  - **R_ST_UOp**：队列里存的不是完整 R_UOp，而是精简结构体，包含 imm、**avail**（各操作数是否就绪）、**tags**（各操作数等的 tag）、sqN、tagDst、storeSqN、loadSqN、opcode、fu、fetchID、fetchOffs 等，**不存**实际寄存器值。  
  - 定义：`src/IssueQueue.sv` 第 58–76 行 `typedef struct packed { ... } R_ST_UOp;`  
  - 队列数组：`src/IssueQueue.sv` 第 77 行 `R_ST_UOp queue[SIZE-1:0];`（SIZE 通常为 8）

- **insertIndex**  
  - 表示当前队列中「有效条目」的个数，即下一个入队要写的位置；有效槽为 `0 .. insertIndex-1`。  
  - 定义与更新：`src/IssueQueue.sv` 第 79 行 `reg[$clog2(SIZE+1)-1:0] insertIndex;`，出队时减 1（约 310 行），入队时加（约 385 行起），分支恢复时重算（约 223–253 行）。

- **就绪更新（谁可以发射）**  
  - **newAvail_c / newAvail_r**：组合/时序逻辑，表示「本周期新就绪的操作数」或「延迟若干拍后就绪」；例如某条指令完成写回（`IN_flagUOp[j].tagDst`）或本周期被发射（`IN_issueUOps[j].tagDst`），等待该 tag 的队列项在对应拍数后置位 newAvail。  
  - 写回立即就绪：`src/IssueQueue.sv` 第 101–106 行，若 `queue[i].tags[k] == IN_flagUOp[j].tagDst` 则 `newAvail_c[0][i][k] = 1`。  
  - 本周期发射、延迟就绪：第 108–121 行，根据 `IN_issueUOps[j].fu` 置 `newAvail_c[0]`（INT/BR/BM）、`newAvail_c[1]`（FPU/FMUL）、`newAvail_c[4]`（MUL 等）。  
  - **queueAvail_c**：把队列项原有的 `queue[i].avail` 与上述 newAvail 合并，得到每个槽每个操作数「当前是否就绪」：`src/IssueQueue.sv` 第 124–130 行，`queueAvail_c[0][i] = queue[i].avail | newAvail_c[0][i]`，`queueAvail_c[1][i]` 再并上延迟就绪（供 MUL/FP 等使用）。

- **deqCandidate_c（出队候选）**  
  - **含义**：位向量，`deqCandidate_c[i]==1` 表示「槽 i 上的指令**本周期可以发射**」。  
  - **定义与赋值**：`src/IssueQueue.sv` 第 175 行 `reg[SIZE-1:0] deqCandidate_c;`，第 176–204 行 `always_comb` 中逐槽计算。  
  - **条件**：`deqCandidate_c[i]` 为 1 当且仅当：  
    - `i < insertIndex`（槽有效）；  
    - `&(queueAvail_c[0][i])`（该条目的所有操作数就绪）；  
    - Div/FDiv 的 doNotIssue 不禁止；  
    - 整数/分支/FP 等不会占满写回（reservedWBs）；  
    - CSR 只在 `i==0 && queue[i].sqN == IN_commitSqN` 时发射（按序）；  
    - Load 的 loadSqN 不超 IN_maxLoadSqN；Store 的 storeSqN 不超 IN_maxStoreSqN；SC 按 commitSqN 顺序等。

- **PriorityEncoder（优先编码器）**  
  - **含义**：组合逻辑模块，输入一个位向量，输出「**最低位为 1 的下标**」（即最小索引）；在 IssueQueue 里用来在多个可发射的槽中选**最老的一条**（下标最小 = 先入队）。  
  - **模块定义**：`src/lib/PriorityEncoder.sv`，参数 `BITS`（如 SIZE）、`N`（输出个数）；输入 `IN_data[BITS-1:0]`，输出 `OUT_idx[0]`（第一个为 1 的位下标）、`OUT_idxValid[0]`（是否存在这样的位）。  
  - **在 IssueQueue 中的使用**：`src/IssueQueue.sv` 第 207–213 行：  
    ```systemverilog
    struct packed { logic[$clog2(SIZE)-1:0] idx; logic valid; } deq;
    PriorityEncoder #(SIZE) penc(deqCandidate_c, '{deq.idx}, '{deq.valid});
    ```  
    即：`deqCandidate_c` 作为输入，`deq.idx` 得到「被选中的槽号」，`deq.valid` 表示是否有至少一个候选（即本周期是否真的发射）。

- **deq（出队选中结果）**  
  - **含义**：`deq.valid` 表示本周期是否发射了一条；`deq.idx` 表示发射的是哪一槽。  
  - 使用：`src/IssueQueue.sv` 第 268–318 行：若 `deq.valid`，则 `deqEntry = queue[deq.idx]`，把该条目的字段填到 `OUT_uop`（第 272–292 行），然后执行队列收缩。

- **collapseMask_c / 队列收缩（collapse）**  
  - **含义**：出队后，被选中的槽空出，后面所有有效条目要**前移一格**，使队列在逻辑上仍是连续的一段 [0, insertIndex-1)。  
  - **collapseMask_c**：`src/IssueQueue.sv` 第 215–219 行，`collapseMask_c[i] = (i >= deq.idx)`，即「下标 ≥ 被出队槽」的槽都要前移。  
  - 实际前移：第 312–317 行，若 `deq.valid`，则对 `i < SIZE-1` 且 `collapseMask_c[i]` 的槽执行 `queue[i] <= queue[i+1]`，并把 `queue[i].avail` 更新为 `queueAvail_c[1][i+1]`；同时 `insertIndex` 减 1（第 310 行）。  
  - newAvail 的移位：第 84–93 行，当发生出队且 collapse 时，`newAvail_r[i][j]` 从 `newAvail_c[i][j+1]` 取，相当于与队列一起前移。

- **入队相关**  
  - **isBaseCand_c**：`src/IssueQueue.sv` 第 140–152 行，表示每条 IN_uop 是否可作为**本队列**的入队候选（`validIQ[PORT_IDX]`、HasFU、loadSqN/storeSqN 与 AGU 端口匹配等）。  
  - **OpDownsample**：从 NUM_UOPS 条候选里按 valid 和 numAllowedEnq_c 选出最多 NUM_ENQUEUE 条，得到 **enqCandidates**；`src/IssueQueue.sv` 第 163–174 行。  
  - 入队写入：第 322–385 行，把 `enqCandidates[i]` 转成 R_ST_UOp 写入 `queue`，并更新 insertIndex。

- **错误预测（branch.taken）**  
  - `IN_branch.taken` 时：`src/IssueQueue.sv` 第 239–259 行，根据 `IN_branch.sqN` 和 `IN_branch.flush` 重算 `insertIndex`，只保留「在正确路径上」的条目（sqN 小于/小于等于 branch.sqN）；并清空本周期输出的 `OUT_uop.valid`（除非该 uop 在错误路径之后，见 255–258 行）。

**相关配置**  
- `Config.sv`：`NUM_ALUS = 3`，`NUM_AGUS = 2` → `NUM_PORTS = 5`；每个端口一个 IssueQueue，共 **5 个**，每个 `PORT_IQ_SIZE[i]=8`；`PORT_FUS[i]` 规定端口 i 接受哪些功能单元（端口 0、1 为 AGU+Atomic，端口 2、3、4 为 ALU/乘/除/分支/CSR 等）。  
- `Core.sv` 约 180–215 行：例化 5 个 `IssueQueue`，另加 `StoreDataIQ` 为 Store 提供数据来源（tag）。

**小结**  
| 项目 | 说明 |
|------|------|
| 作用 | 按 FU 分发的发射队列，用 tag 表示依赖，就绪即发射，实现乱序执行。 |
| 入队 | R_UOp，按 `fu` 与 `validIQ[PORT_IDX]` 进入对应队列。 |
| 出队 | 每周期每队列最多 1 条 IS_UOp → Load → EX_UOp → 各 FU；由 deqCandidate_c + PriorityEncoder 得 deq.idx。 |
| 就绪来源 | 写回总线（IN_flagUOp）+ 本周期发射（IN_issueUOps）的 tag，带延迟。 |
| 数量 | 5 个（3 ALU 端口 + 2 AGU 端口），深度 8；另 StoreDataIQ。 |

## validIQ / validIQ[PORT_IDX]

**是什么**  
`validIQ` 是 **R_UOp** 里的一个位向量，长度为 **NUM_PORTS_TOTAL**。每一位对应一个「发射端口」对应的队列：**validIQ[j] = 1** 表示「这条 R_UOp 要进入端口 j 对应的那个 IssueQueue（或 StoreDataIQ）」；**validIQ[PORT_IDX]** 就是「当前这个 IssueQueue 实例对应的端口」的那一位，即：**这条 R_UOp 是否要进本队列**。

**定义与类型**  
- R_UOp 结构体：`src/Include.sv` 第 588–611 行；其中 **validIQ** 在第 609 行：`logic[NUM_PORTS_TOTAL-1:0] validIQ;`  
- NUM_PORTS_TOTAL：`src/Config.sv` 第 100 行，`NUM_PORTS_TOTAL = NUM_ALUS + 2*NUM_AGUS`（例如 3+4=7）。

**谁赋值（Rename.sv）**  
- 成功输出一条 R_UOp 时，先把 **validIQ** 置为全 1：`src/Rename.sv` 第 351 行 `validIQ: {NUM_PORTS_TOTAL{1'b1}}`，表示「本指令可以进入所有与其 fu 匹配的 IQ」。  
- 若本拍 Rename 因背压没有推进，或某个端口 j 对某槽 i 产生了 stall（`IN_stalls[j][i]`），则下一拍对**没有 stall** 的端口 j 把该槽的 **validIQ[j]** 清 0：`src/Rename.sv` 第 386–388 行：  
  `if (!IN_stalls[j][i]) OUT_uop[i].validIQ[j] <= 0;`  
  即：**被 stall 的端口对应的位保留为 1**，下一拍该 uop 仍会尝试进入该端口的队列；已被接受的端口清 0，避免重复入队。  
- IN_stalls 接口：`src/Rename.sv` 第 12 行 `input wire[NUM_PORTS_TOTAL-1:0][WIDTH_ISSUE-1:0] IN_stalls`，`IN_stalls[j][i]` 表示端口 j 对第 i 条 uop 是否 stall。

**在 IssueQueue 里的用法**  
- 入队候选条件：`src/IssueQueue.sv` 第 141–143 行：  
  `isBaseCand_c[i] = IN_uop[i].validIQ[PORT_IDX] && HasFU(IN_uop[i].fu) && ...`  
  即：只有 **validIQ[PORT_IDX] == 1** 时，这条 R_UOp 才被视为「可以进入本 IssueQueue」的候选；再结合 **HasFU(IN_uop[i].fu)**（本端口是否支持该 fu，第 41–44 行）以及 loadSqN/storeSqN 等条件，决定是否真正入队。  
- 入队时再次检查：第 324 行 `if (enqCandidates[i].validIQ[PORT_IDX])` 后才把 enqCandidates[i] 写入 queue。

**在 StoreDataIQ 里的用法**  
- Store 数据队列对应「NUM_PORTS 之后」的端口，因此用 **validIQ[NUM_PORTS+PORT_IDX]**：  
  - `src/StoreDataIQ.sv` 第 107 行：`IN_uop[i].validIQ[NUM_PORTS+PORT_IDX] && ...`  
  - 第 209 行：`if (enqCandidates[i].validIQ[NUM_PORTS+PORT_IDX])`

**与 PORT_IDX 的关系**  
- 每个 IssueQueue 例化时带参数 **PORT_IDX**（0 到 NUM_PORTS-1）：`src/Core.sv` 第 184 行 `.PORT_IDX(i)`。  
- **Config.sv** 第 99–100 行：`NUM_PORTS = NUM_ALUS + NUM_AGUS`（例如 5），`NUM_PORTS_TOTAL = NUM_ALUS + 2*NUM_AGUS`（例如 7）；前 NUM_PORTS 位对应 5 个主 IssueQueue，多出的位对应 StoreDataIQ。

**小结**  
| 项目 | 说明 |
|------|------|
| 类型与定义 | R_UOp 成员，`logic[NUM_PORTS_TOTAL-1:0] validIQ`，`Include.sv` 第 609 行 |
| 含义 | validIQ[j]=1：这条 R_UOp 要进入端口 j 的队列；validIQ[PORT_IDX]：是否进「本」IssueQueue |
| 赋值 | Rename：输出时全 1（Rename.sv 351 行）；未 stall 的端口下一拍清 0（386–388 行） |
| 使用 | IssueQueue：143、324 行 validIQ[PORT_IDX]；StoreDataIQ：107、209 行 validIQ[NUM_PORTS+PORT_IDX] |

## forward（前递 / 旁路）

**是什么**  
**forward**（常译作**数据前递**或**旁路**）指：当一条指令需要的**操作数**正好是「前面某条指令刚算出来、还没写回寄存器文件」的结果时，**不等待写回 RegFile**，而是直接从**写回总线**或**本周期刚算出的结果**上把该值取过来，作为本条指令的 srcA/srcB。这样能消除或减少 RAW 冒险带来的 stall，提高吞吐。

在 SoomRV 里，**Load 阶段**在给 EX_UOp 填 srcA/srcB 时，会同时看：(1) RegFile 读口；(2) **forward 源**（本周期写回的结果 + 本周期同拍算出的“零周期前递”结果）。若某操作数对应的 **tag** 在 forward 源里匹配到，就用 forward 的 **result** 作为 srcA/srcB，否则才用 RegFile 读出的值（或下一拍再填）。

**相关类型**  
- **ZCForward**（零周期前递）：本周期刚算出的结果，在**同一周期**内被后续指令使用；结构体为 `{ result[31:0], tag, valid }`。定义：`src/Include.sv` 第 970–975 行。  
- **ResultUOp**（写回结果）：各 FU 写回时的 `{ result, tagDst, valid }`，也参与 forward。Load 模块里把「IN_resultUOps」转成与 ZCForward 同形的 **forwards** 数组中的高几项。

**在 Load 模块中的实现（代码位置）**  
- **forward 源合并**：`src/Load.sv` 第 34 行 `NUM_FWD = NUM_ZC_FWDS + NUM_WBS`；第 37–48 行：`forwards[]` 前 `NUM_ZC_FWDS` 项来自 **IN_zcFwd**（零周期前递，如 IntALU 本拍结果），后 `NUM_WBS` 项来自 **IN_resultUOps**（写回总线），每项为 `{ valid, tag, result }`。  
- **按 tag 匹配**：第 50–64 行：对每个需要的操作数（lookups[i] = IN_uop 的 tagA/tagB），与所有 forwards 的 tag 比较，得到 **match[i][j]**；第 67–73 行用 OHEncoder 在匹配项中选一个，得到 **matchIdx**、**matchValid**。  
- **写 srcA/srcB**：第 164–169 行（srcA）：若 `matchValid[i]`，则 `outUOpReg[i].srcA <= forwards[matchIdx[i]].result`（用前递结果）；否则置 **operandIsReg[i][0]=1**，表示该操作数需从 RegFile 读。第 177–182 行（srcB）同理：`matchValid[NUM_UOPS+i]` 时用 `forwards[matchIdx[NUM_UOPS+i]].result`，否则 operandIsReg[i][1]=1。  
- **RegFile 补读**：若上一拍标记了 operandIsReg，下一拍 stall 时（第 189–191 行）从 **IN_rfReadData** 读回并填到 srcA/srcB，同时清 operandIsReg。  
- **组合逻辑输出**：第 110–112 行：输出 EX_UOp 时，若 operandIsReg 为 1，则 **OUT_uop[i].srcA = IN_rfReadData[i]**（或 srcB），否则保持 outUOpReg 里已填的 forward 值。

**零周期前递的来源**  
- IntALU 等 FU 在本周期产生结果后，通过 **ZCForward** 接口直接连到 Load：`src/IntALU.sv` 第 13、28–30 行 `OUT_zcFwd = { result, tagDst, valid }`；`src/Core.sv` 第 292、311、371 行把各 ALU 的 **OUT_zcFwd** 接到 Load 的 **IN_zcFwd**。这样「本拍发射、本拍完成」的指令的结果，可以在同一拍被 Load 里需要该 tag 的 uop 使用。

**小结**  
| 项目 | 说明 |
|------|------|
| 含义 | 操作数不从 RegFile 读，而从「本周期写回」或「本周期刚算出」的结果直接取，减少 RAW 停顿。 |
| 实现位置 | Load.sv：forwards 数组 37–48 行；tag 匹配 50–64 行；srcA/srcB 选择 164–169、177–182 行；RegFile 补读 189–191 行。 |
| 类型 | ZCForward（Include.sv 970–975 行）；ResultUOps 转成同形参与 forwards。 |
| 零周期来源 | IntALU 等 OUT_zcFwd → Core 汇总 → Load IN_zcFwd。 |

## wmask（写掩码）

**是什么**  
**wmask**（write mask）是 **Store 的按字节写掩码**：在一个 32 位字内，**哪几个字节**要被写入，用 4 位表示，每一位对应字中的一个字节。  
- **类型**：`logic[3:0]`（`Include.sv` 第 721 行，AGU_UOp 内；SQ_UOp、ST_UOp 等也有 4 位 wmask）。  
- **约定**：`wmask[i]=1` 表示**第 i 字节**参与写入（i=0 为最低字节，i=3 为最高字节）；Store 时只有 wmask 为 1 的字节会写内存/Cache，为 0 的字节不写。

**在 AGU 中的赋值**（`src/AGU.sv` 第 108–151 行）：  
- **LSU_SB**（存字节）：按 `addr[1:0]` 选一个字节 → `4'b0001`、`4'b0010`、`4'b0100`、`4'b1000`。  
- **LSU_SH**（存半字）：按 `addr[1]` 选低/高半字 → `4'b0011`（低两字节）或 `4'b1100`（高两字节）。  
- **LSU_SW**（存字）：四字节都写 → `4'b1111`。  
- **LSU_SC_W** 等：`4'b1111`。  
- **特殊**：CBO 等管理类操作用 **wmask=0** 表示“非普通数据写”（`StoreQueue.sv` 第 42、287 行：wmask==0 作转义，如 isMgmt）。

**与 Load 的关系**  
Load 不写内存，AGU_UOp 的 wmask 对 Load 无意义；**size** 与 **signExtend** 才决定 Load 的宽度与符号扩展。文档里“Store 写掩码”即指 **wmask**；“Load/Store 访问宽度与符号扩展”对应 **size**、**signExtend**。

**小结**  
| 项目 | 说明 |
|------|------|

## isLrSc / LR-SC（Load Reserved – Store Conditional）

**是什么**  
**isLrSc** 是 AGU_UOp（及后续 LD_UOp 等）里的一个标志位，表示**本条访存属于 RISC-V 的 LR/SC 原子对**（Load Reserved – Store Conditional）。  
- **LR**（Load Reserved，opcode **LSU_LR_W**）：从某地址做一次 Load，并在硬件上对该地址建立一个**保留（reservation）**；若之后到对应 SC 之前有别的 Store 写同一地址，保留会失效。  
- **SC**（Store Conditional，opcode **LSU_SC_W**）：向某地址做 Store；仅当该地址的**保留仍有效**时真正写入并让 rd=0，否则不写且 rd≠0（表示失败）。  
LR 与 SC 成对使用，用来实现无锁的原子读-改-写（如 compare-and-swap 风格）。

**isLrSc 的含义与赋值**  
- **含义**：`isLrSc=1` 表示本条是 **LR** 或 **SC** 中的一条；用于 LoadBuffer/StoreQueue 等做**保留跟踪**、**SC 失败检测**和顺序约束。  
- **类型**：`logic isLrSc`（`Include.sv` 第 726 行，AGU_UOp 内）。  
- **赋值**：**AGU.sv** 第 64 行默认 0；第 82–83 行对 **LSU_LR_W** 置 `aguUOp_c.isLrSc = 1`；第 143–144 行对 **LSU_SC_W** 置 `aguUOp_c.isLrSc = 1`。

**在 SoomRV 中的使用**  
- **LoadBuffer**（`LoadBuffer.sv`）：用 **hasRsv** 等跟踪“当前是否有有效保留”；SC 发射/完成时检查 **storeHasRsv**，若无保留则视为 **SC 失败**，触发 flush 并设 **OUT_branch.isSCFail**（约 313–314、334–338 行）；SC 执行后清除保留（约 390–396 行）；LR 完成时建立保留（约 501 行 `entries[index].hasRsv <= IN_uop[i].isLrSc`）。  
- **Rename**：SC 可能被重命名为“失败时写 1”的伪指令（`isSc[i]`，Rename.sv 89 行）；IssueQueue 对 SC 有按序发射等约束。

**小结**  
| 项目 | 说明 |
|------|------|
| 含义 | 本条为 LR 或 SC，属于 LR/SC 原子对 |
| LR | Load Reserved，建立地址保留；opcode LSU_LR_W |
| SC | Store Conditional，有保留才写且 rd=0，否则失败 rd≠0；opcode LSU_SC_W |
| 定义/赋值 | AGU_UOp.isLrSc，Include.sv 726 行；AGU.sv 82–83、143–144 行 |
| 用途 | LoadBuffer 保留跟踪、SC 失败 flush（isSCFail） |
