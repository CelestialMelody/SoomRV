

### 问题 1：关于 `NUM_BRANCH_PORTS = 2`

**Q: 为什么只有 2 个端口支持分支？需要修改增加吗？**

#### 1. 为什么是 2 个？(设计意图)

虽然这是一个 4 发射（4-wide）处理器，但只配置 2 个分支端口是基于**概率统计**和**硬件代价**的合理折中：

* **指令混合率 (Instruction Mix):** 在大多数通用程序（如 CoreMark、Linux 内核）中，分支指令（Branch/Jump）通常占指令流的 **15% ~ 20%**。这意味着平均每 5-6 条指令才有一条分支。在 4 条指令的一个发射包中，统计上很难遇到同时有 3 条或 4 条都是分支的情况。
* **硬件代价极高:** 分支单元不仅仅是计算跳转地址。它需要：
* 与 **Branch Predictor** 交互（反馈预测结果）。
* 与 **ROB** 交互（处理错误预测恢复 `Branch Recovery`）。
* 如果 4 个端口都能处理分支，就需要 4 套复杂的反馈连线，这会极大增加布线拥塞，导致时序变差（主频降低）。


* **配置现状:** * Port 3: `ALU + Branch`
* Port 4: `ALU + Branch + Div`
* 这种非对称设计 既保证了吞吐，又节省了资源。

#### 2. 需要修改吗？

* **建议：不需要修改。**
* **理由：** 将其改为 3 或 4 带来的 IPC（每周期指令数）提升微乎其微，因为前端取指和程序本身的依赖关系才是瓶颈。目前的 2 个端口已经足够消化 4-wide 前端带来的分支指令流。

### 问题 2：关于 `RF_SIZE_EXP 6` (64 个物理寄存器)

**Q: 只有 32 个额外的物理寄存器用于重命名，需要添加吗？**

#### 1. 现状分析 (非常紧张！)

* **算账：**
* 总物理寄存器 =  个。
* 架构寄存器（RISC-V 规定） = 32 个（实际上 x0 不占，所以是 31 个占用）。
* **可用于乱序执行的“重命名资源”**  个。


* **瓶颈所在：**
* 你的 ROB 大小是 64 (`ROB_SIZE_EXP 6`)。
* 理想情况下，我们希望 ROB 能填满 64 条指令以最大化乱序窗口。
* 但是，因为重命名寄存器只有 ~33 个，如果正在流水的指令大都是写寄存器的（如 `add`, `ld`），**处理器会在 ROB 还没填满时（大约第 33 条指令）就发生阻塞 (Stall)**，因为没有空闲的物理 Tag 分配给新指令了。


* **为什么要设这么小？** * 这通常是为了在 **ASIC 流片**（OpenMPW Shuttle）时节省芯片面积，或者为了缩短寄存器堆的读写延迟（容量越小，速度越快）。

#### 2. 需要修改吗？

* **建议：强烈建议修改！(如果你追求性能)**
* **如何修改：** 将其改为 **7** (即 128 个物理寄存器)。
```systemverilog
`define RF_SIZE_EXP 7  // 改为 128 个

```


* **修改后的收益：**
* 可用重命名寄存器  个。
* 这 **完全覆盖** 了 64 条目的 ROB。这意味着重命名阶段永远不会因为缺寄存器而阻塞，瓶颈将转移到真正的执行单元或 ROB 容量上，能显著释放处理器的乱序性能。


* **代价：**
* FPGA 资源占用增加（Block RAM 或 LUT RAM）。
* `src/Include.sv` 中的 `Tag` 类型会自动变为 7 位宽（`typedef logic[RF_SIZE_EXP:0] Tag;`），这会自动传播到所有模块，**代码兼容性没有问题**。

### 总结

1. **分支端口 (`NUM_BRANCH_PORTS`)**：**保持 2**。性价比最高，改大无益。
2. **寄存器堆 (`RF_SIZE_EXP`)**：**改为 7 (128 entries)**。目前的 64 个是明显的性能瓶颈，改为 128 可以解除这个枷锁，让 ROB 发挥全部潜力。
