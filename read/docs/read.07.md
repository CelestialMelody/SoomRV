恭喜你啃完了 `Core.sv`！这是整个处理器最庞大、最复杂的顶层文件。

作为项目学习者，从 `Core.sv` 中你**不需要**记住每一根连线，但你**必须**提取出以下 4 个核心认知，这构成了你对 SoomRV 的**全局视角**：

### 1. 从 Core.sv 中你应该学到什么？

#### A. 流水线的物理形态 (The Pipeline Shape)

你在 `Core.sv` 中看到了各个模块的实例化顺序，这验证了我们在 `architect.jpg` 中看到的结构：

* **前端:** `IFetch` -> `InstrDecoder`
* **乱序引擎:** `Rename` (分配 Tag) -> `IssueQueue` (排队)
* **执行:** `RegFile` (读数据) -> `ALU`/`FPU`/`LSU`
* **提交:** `ROB` (兜底)

**关键点：** 数据包 (`UOp`) 是不断变胖的。

* `IFetch` 输出原始比特流。
* `Decoder` 输出逻辑寄存器号 (`x1`)。
* `Rename` 输出物理 Tag (`p10`)。
* `Load` 输出 32位数据 (`0x1234`)。

#### B. 控制流的“红绿灯” (Flow Control)

你注意到了大量的 `stall` 信号吗？这是乱序处理器的**反压 (Backpressure)** 机制。

* **`sqNStall`**: ROB 满了，告诉前端“别取指了，我记不下了”。
* **`RN_stall`**: Rename 满了（物理寄存器耗尽），告诉解码器“停下”。
* **`IQ_stalls`**: 发射队列满了，告诉 Rename “别发了”。
**结论：** 整个流水线就像一条传送带，任何一个环节堵塞，都会级联地暂停最前面的取指。

#### C. “一键重置”机制 (Global Flush)

你看到了 `branch` 和 `mispredFlush` 信号连接到了几乎所有模块（IFetch, Rename, IssueQueue, ROB...）。
**结论：** 当分支预测错误时，处理器不像简单的 CPU 那样只清空两级流水线，而是必须**全局广播**这个信号，让所有模块瞬间丢弃当前处理到一半的“错误路径上的指令”。

#### D. 内存子系统的复杂性

`LSU` 并不是孤独工作的。它周围围绕着 `StoreQueue` (处理写)、`LoadBuffer` (处理读冲突)、`PageWalker` (处理虚存)、`CacheLineManager` (处理 L1 Cache)。
**结论：** 访存是 SoomRV 中最复杂的独立王国，它有自己的调度逻辑。

### 2. 接下来阅读什么？

既然你已经看懂了“地图”（Core.sv）和“字典”（Include.sv），现在我们要深入**心脏**。

乱序处理器的核心魔法在于：**如何把程序员看到的“顺序执行”骗成硬件层面的“乱序执行”，最后再骗回来？**

这个魔法由两个模块共同完成：**Rename（重命名）** 和 **ROB（重排序）**。

建议的阅读顺序如下：

#### **第一站：重命名逻辑 (The Renamer)**

这是乱序的起点。在这里，逻辑寄存器（x1, x2）消失了，物理 Tag 诞生了。

* **目标文件：**
1. **`src/Rename.sv`** (主逻辑)
2. **`src/RenameTable.sv`** (映射表 RAT)


* **看点：**
* 它是如何从 `FreeList` 里拿出一个空闲 Tag 分配给新指令的？
* 它是如何通过 `RAT` 表找到源操作数（Source Operands）对应的 Tag 的？
* 它是如何处理分支预测失败时的**状态恢复**（Walkback / Snapshot）的？



#### **第二站：重排序缓冲区 (The ROB)**

这是乱序的终点。它保证了指令虽然是乱着做的，但是是按顺序“生效”的。

* **目标文件：**
1. **`src/ROB.sv`**


* **看点：**
* `sqN` 是怎么分配和回收的？
* `Commit`（提交）指针是怎么移动的？
* 当发生异常或预测错误时，它是如何指挥全场进行回滚的？
